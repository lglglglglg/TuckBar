# macOS 菜单栏收纳工具：竞品与技术立项分析

> 版本：v0.1  
> 日期：2026-09-07  
> 项目性质：全新独立 macOS 应用  
> 当前阶段：技术可行性验证前

## 1. 直接结论

这个项目值得做，但不能把它当成一个普通 SwiftUI 小工具。

用户真正需要的不是“让图标暂时消失”，而是：

> 在带刘海、菜单栏空间紧张和应用菜单较长的情况下，把低频状态项收起到一个稳定的聚合面板；需要时能看见实时状态，也能像点击原图标一样打开其菜单。

这与 [Better365 iBar](https://www.better365.cn/ibar.html) 和 [Ice](https://icemenubar.app/) 属于同一产品类别。新项目应独立开发；Notchly 只作为问题出现的真实场景，不与本项目合并。

立项的最大风险不是界面，而是 macOS 没有公开 API 允许一个应用直接接管其他应用的菜单栏图标。现有工具采用的是多种间接机制，系统大版本更新后容易失效。因此首个里程碑必须是技术验证，而不是先画完整设置页。

## 2. 已确认的真实场景

当前截图中，右侧有大量第三方常驻状态项；带刘海屏幕把可用空间切成左右两段。当图标继续增加、前台应用菜单较长，或顶部工具占用中央视觉区域时，会出现：

- 图标被刘海挡住或被 macOS 直接省略；
- 即使“展开隐藏区”，横向空间仍然不够；
- 用户看不到图标当前状态，也无法点击其菜单；
- 为了解决一个图标而退出其他常驻应用，体验很差。

因此“只在原菜单栏横向展开”不足以解决本项目的核心场景，首版最终必须包含菜单栏下方的聚合面板。

### iBar 的核心设计

iBar 官网明确展示两种模式：

1. **普通模式**：图标仍在原菜单栏，点击控制项后横向隐藏或显示。
2. **聚合模式**：原图标收起，菜单栏下方出现浮动窗口，集中显示隐藏图标。

它对本项目最有价值的不是设置项，而是把“刘海导致横向展开仍然无效”作为主问题。聚合浮窗才是用户可感知的核心价值。

### Ice 的核心设计

Ice 官网展示了四个主要能力：

- 在菜单栏下方显示隐藏项目；
- 用拖拽界面安排项目；
- 自定义菜单栏外观；
- 搜索菜单栏项目和调整间距。

Ice 的公开仓库采用 GPL-3.0。可以研究其公开架构和交互，但若本项目计划使用 MIT 或闭源商业许可，不应复制或改写其 GPL 代码。

## 4. 现有工具的技术原理

### 4.1 普通隐藏：用超长分隔状态项把图标推出屏幕

macOS 的公开 `NSStatusItem` API 只能创建和控制本应用自己的状态项，不能直接隐藏别的应用的状态项。[Apple 也提醒菜单栏空间有限，状态项不保证始终可见](https://developer.apple.com/documentation/appkit/nsstatusbar)。

Hidden Bar 公布的核心做法是：

- 创建一个切换按钮和一个分隔状态项；
- 用户按住 Command，把想隐藏的图标拖到分隔项左侧；
- 收起时把分隔项长度放大到数千点，把左侧图标推到屏幕外；
- 展开时把分隔项恢复成正常宽度。

优点是简单、低资源、普通模式无需屏幕录制或辅助功能权限。缺点是图标实际仍在系统菜单栏里；空间本来就不足时，展开后仍可能位于刘海后面或屏幕外。

### 4.2 聚合面板：识别窗口、捕获图标、转发点击

菜单栏下方的聚合面板通常需要组合以下能力：

1. 用 Core Graphics 窗口列表或辅助功能树识别菜单栏状态项；
2. 用 ScreenCaptureKit 或窗口截图获取其他应用图标的当前外观；
3. 在无边框 `NSPanel` 中重新排列这些图标快照；
4. 用户点击快照时，通过辅助功能动作或合成鼠标事件触发真实状态项；
5. 必要时短暂把目标图标移回可见区域，再点击并恢复布局。

[MenubarHide 的公开说明](https://github.com/junior-rj/menubar-hide)记录了一个现实限制：离屏窗口无法直接被 ScreenCaptureKit 捕获，因此可能需要短暂展开、截图后再收起。这会带来闪烁、延迟和布局错乱风险。

[Apple 的 ScreenCaptureKit 示例](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos)也说明，首次捕获其他应用窗口需要屏幕录制权限，授权后通常需要重新启动应用。点击转发或读取其他应用的 UI 则需要辅助功能权限。

### 4.3 私有接口

更强的工具可能使用 CoreGraphics/SkyLight 等未公开能力识别或移动状态项。它们能改善体验，却有三个问题：

- macOS 更新时没有兼容承诺；
- App Store 审核风险更高；
- 崩溃、图标错位和系统菜单失效更难排查。

本项目的首版不应把私有 API 作为唯一可用路径。可以建立隔离的实验适配层，但公开能力和降级模式必须始终存在。

## 5. 推荐产品定位

一句话定位：

> 一款为刘海 Mac 设计的轻量菜单栏收纳器：平时只留重要图标，需要时在下方整齐展开，所有图标都看得见、点得到。

差异化不放在“功能最多”，而放在以下五点：

1. **可靠优先**：任何时候都有恢复布局、重新扫描和临时全部展开入口。
2. **聚合优先**：不是把下方浮窗当高级功能，而是把它作为刘海机型的默认体验。
3. **权限透明**：普通模式零额外权限；开启聚合模式时逐项解释屏幕录制和辅助功能用途。
4. **轻量原生**：Swift + AppKit 为核心，SwiftUI 只负责设置和普通界面，不引入 WebView。
5. **中文体验完整**：首次引导、权限说明、故障恢复和术语都用正常中文表达。

## 6. 第一版范围

### 必须有

- 常显区与收起区；
- 普通横向显示模式；
- 菜单栏下方聚合面板；
- 点击、悬停、全局快捷键三种唤出方式；
- 可配置自动收起延时；
- 登录时启动；
- 带刘海、无刘海和外接显示器定位；
- 权限状态检查、重新授权指引、恢复全部图标；
- 应用崩溃或退出后不把用户图标永久留在不可见位置。

### 首版不做

- 菜单栏颜色、阴影、圆角等主题美化；
- 按电量、Wi-Fi、专注模式或前台应用自动触发；
- 云同步、账号和跨设备配置；
- Touch ID 锁定隐藏图标；
- 自定义脚本、组件和复杂搜索；
- 与 Notchly 或其他本地项目进行功能合并。

## 7. 推荐技术架构

```text
MenuBarOrganizerApp
├── StatusBarController        # 本应用的切换项与分隔项
├── HidingEngine               # 普通模式：长度切换、分区和恢复
├── MenuItemDiscovery          # 状态项枚举、归属识别和缓存
├── IconCaptureService         # 图标快照与刷新
├── ActivationService          # AX 动作 / 事件转发 / 临时移回
├── AggregatePanelController   # 菜单栏下方 NSPanel
├── DisplayCoordinator         # 刘海、多显示器、分辨率和热插拔
├── PermissionCoordinator      # 屏幕录制与辅助功能权限
├── RecoveryService            # 异常退出、错位和重建布局
└── SettingsStore              # 本地配置与版本迁移
```

推荐：

- Swift 6；
- AppKit 主导窗口、菜单栏和事件处理；
- SwiftUI 用于设置页、引导页和聚合面板内容；
- `SMAppService.mainApp` 管理登录启动；
- `UserDefaults` 保存轻量设置，首版不引入数据库；
- 先支持 macOS 14 及以上，重点验证 macOS 26；macOS 27 在正式兼容验证前只标记为实验支持。

## 8. 系统版本风险

2026 年的开源项目已经记录了明显的系统断层：Hidden Bar 的超长分隔项方案在 macOS 27 Beta 的新菜单栏架构中失效；SaneBar 也明确披露 macOS 27 会破坏现有菜单栏管理方案。这意味着：

- 不要在完成实机验证前承诺 macOS 27；
- 把所有系统相关操作放在独立适配层；
- 普通隐藏、聚合展示和点击激活分别做能力检测；
- 一项能力失效时，应用要降级并提示，而不是让图标静默消失；
- 发布前至少测试 macOS 14、15、26，以及当时最新的 27 测试版或正式版。

## 9. 第一个技术验证里程碑

先做一个只有工程界面的 Spike，不做品牌和完整设置：

1. 创建切换项与分隔项，验证 10 个第三方状态项的收起和恢复；
2. 枚举并识别状态项，记录哪些图标能稳定获得所属应用和位置；
3. 在下方 `NSPanel` 显示图标快照；
4. 从面板点击至少 8 类常见图标，确认能打开真实菜单；
5. 验证睡眠唤醒、应用重启、状态项晚启动和退出恢复；
6. 验证内建屏、外接屏、切换主屏和插拔显示器；
7. 在 Notchly 运行和展开时做一次共存测试，但不产生任何代码依赖。

### 通过标准

- 连续收起/展开 100 次不丢失图标顺序；
- 聚合面板打开时间主观无明显等待，目标暂定小于 200ms；
- 面板中的图标能反映连接、录音、同步等状态变化；
- 点击面板图标后，菜单出现在正确屏幕且可以继续交互；
- 强制退出本应用后，重启能够恢复或一键重建布局；
- 不授权高级权限时，普通模式仍然可用。

若“离屏捕获 + 点击转发”无法达到上述稳定性，应暂停完整开发，先改为无需实时快照的应用列表方案，不应继续堆叠界面功能掩盖底层问题。

## 10. 发布与许可建议

- 原型和 Alpha 优先使用 Developer ID 签名、公证和直接分发，便于调试权限与系统行为；稳定后再单独评估 App Store。
- 如果参考 Hidden Bar 或 SaneBar 的 MIT 实现，保留其许可与版权声明，并明确记录实际复用内容。
- Ice 为 GPL-3.0；除非决定整个衍生项目按 GPL 分发，否则只研究行为和公开架构，不复制其代码。
- 首版所有捕获只在内存中处理，不保存菜单栏截图，不上传图标、应用列表或使用数据。

## 11. 下一步

下一步不是继续扩充竞品表，而是建立独立 Swift 工程，完成“普通隐藏 → 聚合显示 → 点击激活 → 异常恢复”这条最短技术闭环。闭环通过后再确定正式产品名、图标和视觉语言。
